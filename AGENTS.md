# Website agent instructions

makoa.link is a personal React 18 + Vite 6 site in `my-app/`. Each page is a self-contained directory: `src/Bio`, `src/Hurricane`, `src/Royalty`, `src/Snow`, `src/Tectonics`, and Photos on unmerged branches. Each has its own data pipeline and README. The code repository is public (`rslmart/Website`, branch `master`). Deploys run locally to S3 + CloudFront through `my-app/deploy.sh`. See `README.md`.

## Agent roles

- **Conductor**: The persistent project orchestrator (the Website orchestrator thread). It owns goal readiness, priorities, dependency and file-overlap checks, delegation, canonical plan updates, serial integration, and everything outward-facing. That means any `git push` to any remote or branch (including the `plans/website` repo), merges to `master`, any `deploy.sh`/`npm run deploy` run (including `--dry-run`, which still loads `.env.deploy` and calls AWS), any `aws` CLI call or S3 upload (including the Hurricane `hurricane-ir/` imagery upload), and GitHub branch or repository changes. Each needs the user's explicit approval. Preferred tier: Strategic. Keep an already-running session's model.
- **Goal Worker**: Owns one assigned goal or independently testable slice, its implementation and its focused checks (`npm run build`, pipeline tests, local preview). Balanced by default. Up to two workers may write at once, each in its own isolated T3-managed worktree when isolation is available; otherwise only a single writer. No recursive delegation, pushes, deploys or edits to canonical plans.
- **Reviewer**: Independently inspects a given diff, candidate or plan and reports actionable correctness, regression, privacy and acceptance-gap findings, plus simplification opportunities (user preference 2026-11-17: always look for places to simplify without weakening safety, authority or correctness; scope-changing simplifications go to the user). Read-only by contract. Balanced normally; Strategic for personal-data publication, deploy/infrastructure or architecture changes.
- **Explorer**: Investigates a bounded question: code paths, data sources, Wikipedia/Wikidata/NOAA/WSDOT and other primary documentation, and prior art for a goal's research step. Read-only by contract. Fast normally; Balanced for difficult investigations. Returns sources with check dates, uncertainties and a concise recommendation.

## Agent coordination

The user requested this architecture on 2026-11-16, modeled on the t3-mission-control project's standard Conductor/worker setup and adapted to this site. Follow [plans/website/agents/architecture.md](plans/website/agents/architecture.md) and the [dispatch checklist](plans/website/agents/dispatch.md).

- **Delegation:** delegate only useful independent work. At most four agents are active at once, including the Conductor. Up to two of them may be Goal Workers; Explorers and Reviewers may use any free slot. Don't keep an idle standing team.
- **Task brief:** start every delegated task with a standalone `[mission-control-goal:GOAL_ID]` line (the goal the agent actually works on) followed by a standalone `[mission-control-role:ROLE]` line naming one of the roles above, pass the matching T3 `delegate_task` role, and name the provider, model and effort explicitly; and fill in the matching brief in `plans/website/agents/`. Each brief states the goal ID, scope, owned files, starting commit, acceptance criteria, checks, budget and stop conditions. Workers do not start their own agents.
- **Shared files:** these belong to one writer at a time. Under `my-app/`: `src/index.jsx`, `src/Home.jsx`, `src/global.css`, `src/index.css`, `src/components/`, `src/hooks/` (`useViewport` is used by four pages), `index.html`, the root-level `public/` files (icons, `manifest.json`, `robots.txt`), `package.json`, `package-lock.json`, `vite.config.js`, `deploy.sh` and `my-app/.gitignore`. At the repository root: `README.md`, `.gitignore` and this file. Parallel workers may each own a different page directory and its `public/<page>/` data. Changes to shared files are sequenced or given to one worker.
- **Isolation:** independent write tasks use supported T3 worktree delegation; never create an unbound checkout in the shell. If isolation isn't available, keep one writer and run read-only work in parallel.
- **Integration:** only the Conductor changes the canonical plan files in `plans/website/`. Workers report the plan changes they want instead of making them. The Conductor integrates serially and has substantive changes reviewed. Small, reversible edits need no review agent.
- **Secrets and personal data:** never print, commit or copy `.env*` values (Mapbox token, deploy configuration) or AWS credentials, and never put them in web queries or external requests. The same goes for personal location data (photo GPS, flights, booking references/PNRs, stays, drives). That data is committed or published only as `plans/website/DECISIONS.md` allows. Flight exports drop the PNR and seat columns and all upcoming flights before they are committed.
- **Worktrees:** `plans/website/` is git-excluded, so new worktrees don't contain it, and a worktree's copy of this `AGENTS.md` (tracked since 85cc150) is only as current as its base commit. Briefs therefore point to the main checkout by absolute path: `/Users/russellmartin/Personal/Website/AGENTS.md` and `/Users/russellmartin/Personal/Website/plans/website/`. Worktrees have no `node_modules` or `.env.local`. Workers may run `npm ci` in their own worktree for builds, but never copy `.env*` files. Mapbox-dependent pages are checked visually by the Conductor in the main checkout.
- **Tracking:** link each goal or session before work (Track work, or `track-goal PROJECT_ID GOAL_ID THREAD_ID`). Keep estimate baselines.
- **Limits:** role labels do not grant or enforce permissions. Adopting this architecture starts no agents.

## Mission Control project workflow

This project uses T3 Mission Control. Read `plans/website/GOALS.md`, `ROLLOUT.md`, `DECISIONS.md`, and `HANDOFF.md` in that folder before continuing. Edit these repository files directly; the app reads them and its JSON checklists are a cache. Preserve stable item IDs, progress, estimates, acceptance criteria, and project-specific agent rules. Update HANDOFF.md after milestones or before leaving unfinished work.

Read `plans/website/MISSION_CONTROL.md` for shared app capabilities, provider profiles, and repository routing. Orchestrators may suggest a project-specific tool when evidence indicates it would help. Submit it as a pending tool proposal with problem, scope, acceptance criteria, alternatives, risks, total build token/time estimate and forecast time saved per use/weekly frequency/maintenance/confidence. The user alone approves it as a goal or declines it in Mission Control; agents must not approve their own proposals or start tool development merely because a suggestion exists. See the shared document for submission commands.

Research each goal before starting it, in depth for large top-level goals. Check this codebase and related repositories for existing or partial implementations, reusable code, earlier attempts and recorded decisions; check the internet for prior art such as libraries, official APIs and documentation, open-source projects and published designs that accomplish the goal or a similar one; consult the model's own knowledge of established approaches and pitfalls, treated as unverified until checked against primary sources; and do any other research that makes the goal easier or more correct. Scale depth to size and risk. Record sources with check dates, findings, a reuse-versus-build recommendation and resulting scope or estimate changes in the goal before implementation; do not repeat recorded research that is still current. Research is read-only and does not authorize installs, account connections, service actions or wider scope.

Review material plans before accepting them. When a planner creates a new top-level goal, re-slices an in-progress goal into tasks, or changes approval, authority or other safety design, run an independent read-only plan review before the plan counts as accepted. The reviewer checks that acceptance covers the user's actual request, every needed piece of work is owned, dependencies and order are right, nothing conflicts with recorded decisions or existing goals, criteria are testable, estimates are sane against comparable actuals without unexplained scope growth, and the research step was done. The planner or orchestrator fixes findings before implementation starts. Recording user decisions and small wording edits need only orchestrator validation. Always look for places to simplify: plan and code reviewers check every plan or diff for a simpler way to meet the same need (code or steps that can be removed, existing pieces to reuse instead of new ones, duplicated checks or layers, scope beyond the request, or a simpler design with the same safety) and report ranked simplify findings. Never trade a safety, authority or correctness guarantee for simplicity; a simplification that changes scope or a user decision goes to the user.

For every external-service integration goal, check current official plugins and MCP servers before implementation, at least as a feature reference. Record primary links and check date, desired-feature to verified tool/API/CLI coverage, permissions/version/site requirements, and gaps. Compare direct reuse with a native adapter; do not assume MCP availability means complete integration. Keep read/write capabilities and connection state explicit, re-estimate expanded scope, and preserve reference findings in the goal and completion record. Research does not authorize installing plugins, connecting accounts or executing service actions.

When the user asks what is next, ground the recommendation in an existing ready goal or subgoal, and give its stable ID, short outcome/next acceptance slice, why it comes next, scope, active-time and total input/output-token ranges, confidence and assumptions. Use the supplied CLI command next PROJECT_ID (optionally GOAL_ID) to inspect ready work and current orchestrator provider/quota. If the next slice lacks an estimate, save an estimated goal/subgoal before presenting a tracked forecast. Preserve original baselines; distinguish remaining work from total estimates. Report estimated token cost as a percentage of total and remaining provider allowance only when a compatible token denominator or validated model/account calibration exists. Current T3 quota windows expose percentages without token limits, so cost percentage is unknown; show reported remaining percentages, resets and staleness instead of inventing conversion. Keep Cursor pools separate. A recommendation alone does not start work.

Before marking a goal or subgoal done, append a dated completion record to GOAL_HISTORY.md in this canonical folder. Include stable goal ID and project ID, delivered scope/acceptance evidence, findings during implementation, changes made because of those findings, technical implementation details/documentation, tests/verification, commits/releases, original and latest forecasts, measured active time/tokens with coverage, variance/lessons, limitations and follow-ups. Use ACTUALS.json when available; exclude input waits, avoid double-counting tokens, preserve baseline estimates and mark missing historical metrics unknown. Completion records are the durable reference; keep HANDOFF.md focused on current continuation context. Never claim in-progress investigation is complete.

This integration adds planning and visibility; it does not replace the rest of this project's contract, change running agents, or authorize publishing code.
